# crew-init

You are setting up this repo's `.t3/` toolbox so installed T3 crews can run here.
Arguments: zero or more crew ids.

## Rules

- Use the T3 tools for crew data: t3_crews_list, t3_crews_get, t3_crews_toolbox, t3_crews_validate.
- Only write inside `.t3/`. Only add entries; never change, reorder or remove existing ones.
- Never edit provider configs (.mcp.json, .cursor/, .vscode/, .claude/, .codex/), never install
  packages, never start MCP servers, never commit or push.
- Never write or display a secret value. Use `${secret:NAME}` and tell the user to add NAME in
  Settings, Crews, Secrets.
- Every proposed item needs one line of evidence from this repo. No evidence: leave it
  unresolved and say so. Never invent a command you found no trace of.

## Steps

1. Crews. If no ids were given, call t3_crews_list, list the installed crews and ask which to
   set up, then end your turn. Do not read the repo first. If an id is unknown, list the
   installed crews and ask.
2. Needs. For each crew, call t3_crews_get. The `unresolved` names are what this repo has to
   define; roles already grant them in crew.yaml. Call t3_crews_toolbox for what `.t3/` already
   has, its toolbox mode, and the MCP servers found in the repo's provider configs.
3. Evidence. Read the repo: package.json scripts with the package manager from the lockfile
   (pnpm-lock.yaml, yarn.lock, bun.lock or bun.lockb, package-lock.json) and workspace roots,
   Makefile and justfile targets, Cargo.toml, pyproject.toml and tox.ini, go.mod, AGENTS.md,
   CLAUDE.md, CONTRIBUTING.md, README.md, .claude/skills/, .agents/skills/.
   Match by name first (unit-tests to a script named test or test:unit), then by the crew's
   own context: role descriptions and the step tasks that use the name.
4. Proposals.
   - Tools: tools.yaml entries with description, run and timeoutSeconds (600 for tests and
     builds, 120 for lint and typecheck unless the repo says otherwise).
   - MCP servers: take them from `mcpImports` in t3_crews_toolbox. Each is already converted
     to mcp.yaml form with secrets as `${secret:NAME}`; copy `server` as is. An import with
     `unsupported` is listed as not supported, with its reason. Never copy env values from the
     provider config files yourself.
   - Skills: a wrapper `.t3/skills/<name>/SKILL.md` for a skill in .claude/skills/ or
     .agents/skills/: keep the original's name and description in its frontmatter, and in
     the body tell the agent to read the original file by its repo path. Never copy the
     original's body. Only a skill about repo conventions (repo-conventions, conventions,
     code-style and similar names) with no skill of that name gets a new wrapper that points to
     AGENTS.md, CLAUDE.md, CONTRIBUTING.md or README.md, with a description that ends in
     "(generated by /crew-init, review)". Any other skill with no skill of that name stays
     unresolved: write nothing for it.
   - Extras: useful repo items no crew asked for (an MCP server, a lint script), off by
     default. Pick the roles each extra suits from their tags and descriptions; a UI tool such
     as Storybook suits roles tagged frontend. If accepted, define it and grant it on its own:
     under `tags.<tag>` when the roles it suits share a tag, otherwise to each exact role
     (`crews.<crew>.<role>`). Never use `crews."*"."*"` unless the user asks for it.
   - A name `.t3/` already defines is left alone. If its definition differs from what you
     would propose, report the clash; never change it.
5. Dry run. Call t3_crews_validate with the full proposed text of every file you would
   change or create (existing text plus your additions). Fix errors in your proposals.
6. Plan. Show, per crew: the needed items with their evidence line, the names left
   unresolved, the optional extras, and the secrets the user must add in Settings, Crews,
   Secrets. Ask for approval ("yes", "yes + extras", or changes) and end your turn.
   Nothing is written before the user approves.
7. Write. If this thread cannot edit files (plan mode or read-only), say you need edit
   access to write the files and stop. Otherwise apply only what was approved:
   - Add new keys at the end of their map (`tools:`, `servers:`, `tags:`, `crews.<id>:`), editing the
     text in place. Keep existing keys, values, comments and order exactly as they were.
   - A new YAML file starts with a comment saying /crew-init created it. A new crews.yaml also
     starts with the schema header
     `# yaml-language-server: $schema=https://raw.githubusercontent.com/Steve524/t3code/main/docs/fork/schema/crews-toolbox.json`.
     mcp.yaml and tools.yaml have no schema, so they get no header. A new SKILL.md starts with
     its frontmatter; nothing comes before the first `---`.
   - Never create .t3/crews/ and never change the toolbox mode.
8. Check. Call t3_crews_get for each crew again, against the files on disk. If your additions
   cause errors, fix them or report what you could not fix. Report each crew's status in this
   project and what is still unresolved. Check whether .t3 is gitignored
   (`git check-ignore .t3/crews.yaml`). If it is, say the files won't be committed and show the
   lines to add to .gitignore (`!.t3/`, `.t3/*`, then `!.t3/crews.yaml`, `!.t3/mcp.yaml`,
   `!.t3/tools.yaml`, `!.t3/skills/`) without adding them.

Running again is safe: when nothing is missing, report each crew's status and say there is
nothing to add.
